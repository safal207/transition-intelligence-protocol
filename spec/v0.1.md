# Transition Intelligence Protocol v0.1

Status: Draft

## Purpose

TIP v0.1 defines the minimal record format for reasoning about a transition before action is taken and recording what happened when the result is later reviewed.

The goal is simple:

```text
Do not jump from state directly to action.
```

A valid TIP record should pass through:

```text
State -> Tension -> Cause -> Transition -> Cooperation -> Action
```

A reviewed record may then close the loop:

```text
Action -> Review -> Next State
```

## TIP Record

A TIP Record is a structured explanation of why an action is considered, what transition it may create, whether cooperation remains stable after the action, and what was observed during review.

## Required fields

| Field | Meaning |
| --- | --- |
| id | Stable identifier for the record. |
| title | Human-readable title. |
| state | Current configuration of the situation. |
| tension | Pressure that makes the current state unstable or incomplete. |
| cause | Reason the transition exists or action may be considered. |
| transition | Movement from current state toward a possible next state. |
| cooperation | Stability check across participants. |
| action | Concrete next step. |
| status | Current lifecycle state of the record. |

The `review` field is conditional. It is optional before review and required by a semantic invariant when `status = reviewed`.

## Status values

| Status | Meaning |
| --- | --- |
| draft | The record is still being formed. |
| clarified | State, tension, and cause are clear enough for review. |
| blocked | Action is not justified. |
| committed | Action is allowed as the next step. |
| reviewed | The result has been inspected after action and review notes are present. |

## Minimal invariants

A record is invalid if it contains an action but does not contain state, tension, cause, transition, and cooperation.

```text
state + tension + cause + transition + cooperation -> action
```

A record with `status = committed` must contain a non-empty, concrete `action.summary`. A commitment without a named action is not operationally meaningful.

A record with `status = reviewed` must contain a non-empty `review.summary`. A reviewed status without an observed result creates a false claim that the action was inspected.

A record with `status = committed` cannot have `cooperation.defection_risk = high`. A committed action must not hide a known high risk that important participants will abandon or destabilize the transition.

## Causal space-time transition guard

Cause confidence alone is not sufficient to authorize an action. TIP v0.1 checks a low-confidence commitment as a small causal experiment across four dimensions:

```text
weak causal evidence
-> bounded impact in space
-> fast feedback in time
-> highly reversible transition
-> explicit review point
-> new evidence and next state
```

For v0.1, `cause.confidence < 0.5` is treated as operationally low. A committed record below this threshold is valid only when all of the following are true:

1. `transition.reversibility = high`;
2. `transition.impact_scope` is `local` or `bounded`;
3. `transition.feedback_latency` is `immediate` or `short`;
4. `action.review_after` names a concrete review point;
5. cooperation does not have high defection risk.

This is a risk-control guardrail, not a claim that `0.5` separates truth from falsehood. Low confidence may justify a bounded pilot, observation, clarification step, or evidence-gathering action. It does not justify exposing the whole system to a weak causal hypothesis.

High confidence also does not prove safety or truth. It only means that this particular low-confidence guard no longer applies; the remaining transition and cooperation checks still matter.

## Field model

### State

The state describes the current situation before change.

It should include:

- actors;
- context;
- known facts;
- constraints.

### Tension

The tension describes why the state cannot simply remain as it is.

It may include:

- ambiguity;
- urgency;
- conflict;
- risk;
- opportunity;
- unmet need.

### Cause

The cause describes why the transition is meaningful or why action may be considered.

It should include:

- cause type;
- summary;
- supporting signals;
- confidence.

### Transition

The transition describes movement from the current state to a possible next state.

It should include:

- from state;
- to state;
- trigger;
- reversibility;
- expected consequence.

It may also include:

- `impact_scope`: `local`, `bounded`, or `systemic`;
- `feedback_latency`: `immediate`, `short`, `long`, or `unknown`;
- uncertainty.

`impact_scope` represents the spatial reach of the action across people, components, cohorts, or systems. `feedback_latency` represents how long the system expects to wait before useful consequences can be observed.

### Cooperation

The cooperation check asks whether the transition remains stable among important participants.

It should include:

- participants;
- shared upside;
- risk of unilateral breakage;
- stability level;
- recommendation.

### Action

The action describes the smallest justified next step.

It should be:

- proportional to the tension;
- based on cause;
- compatible with cooperation;
- reviewable later.

For low-confidence commitments, `review_after` is mandatory because the action is justified as an evidence-producing experiment, not as a final proof of the cause.

### Review

The review describes what was actually observed after action.

It may include:

- a concise review summary;
- the actual consequence;
- evidence references;
- the next observed state.

Review does not prove that the action caused every observed result. It records the observed outcome and keeps causal uncertainty visible.

## Example

```json
{
  "id": "tip.example.startup_pivot",
  "title": "Startup pivot decision",
  "status": "committed",
  "state": {
    "summary": "The product has early interest but weak retention.",
    "actors": ["founder", "early users", "contributors"],
    "constraints": ["limited time", "unclear positioning"]
  },
  "tension": {
    "summary": "Users understand the idea but do not return consistently.",
    "kind": "unmet_need"
  },
  "cause": {
    "cause_type": "constraint",
    "summary": "The current product solves a broad problem, not an urgent narrow pain.",
    "supporting_signals": ["weak retention", "unclear user habit"],
    "basis": "Observed usage pattern",
    "confidence": 0.72
  },
  "transition": {
    "from": "broad productivity product",
    "to": "narrow decision-support protocol",
    "trigger": "retention weakness",
    "reversibility": "medium",
    "expected_consequence": "clearer value proposition"
  },
  "cooperation": {
    "participants": [
      {"name": "founder", "goal": "focus", "risk": "overbuilding"},
      {"name": "early users", "goal": "clear benefit", "risk": "confusion"}
    ],
    "shared_upside": "Sharper product category and easier validation.",
    "defection_risk": "medium",
    "stability": "fragile",
    "recommendation": "clarify"
  },
  "action": {
    "summary": "Run one narrow pilot before changing the whole product.",
    "review_after": "pilot completion"
  }
}
```

## Version goal

v0.1 is intentionally small. It exists to make one transition inspectable before action and reviewable after action.

Future versions can calibrate confidence policies using real cases and can add scoring, canonical transition states, replay, CLI tooling, and integration with agent traces.
